# DR7 `FBPRG16.EXE` — the BA1FB parallel-port AVR programmer, disassembled

> **Register:** src-75 · **Source archives:** `samples/archive/dr7/avrprogrammer.zip`, `avrsetup.zip`
> **Examined:** 10 October 2026 · **Type:** MZ triage + static 16-bit real-mode disassembly
> **Execution:** none; no DOS binary was run and no programmer hardware was connected.

A fresh DR7 sample after the MAKInterface work: not another disassembly of Disavr3, but a 1990s AVR in-system programmer whose source archive happens to carry its own wiring diagram. The useful result is the bridge from strings to machine behavior: this is a plain DOS application that bit-bangs AVR serial programming through a PC parallel port, with the printer-port ACK input used as MISO.

## One executable, two archives

They are byte-identical; the later ZIP timestamp does **not** identify a later executable build. Their companion `FBPRG.CFG` files are different three-byte blobs—`ff 01 00` in `avrprogrammer.zip`, `8b 04 00` in `avrsetup.zip`—so those are environment/configuration snapshots, not a reason to count the program twice. Their schema has not been decoded here. `avrsetup.zip` also carries `AVRSETUP.EXE` and `HEXCSUM.EXE`; those are separate, unanalyzed targets.

The repository's archive provenance ledger pins `avrprogrammer.zip` to the 2000-09-15 22:47:17 capture (51,069-byte archive, SHA-256 `16e807f3ec181cdd4d551fa6647f45f19f215a2c3ee662c86e5f823248812077`) and `avrsetup.zip` to 22:42:03 (70,758 bytes, SHA-256 `876497f84feb40c565081d9dd714602f420c9b8e82a5f13f45648d000cd67b1b`); both Wayback URLs are recorded in `samples/archive/PROVENANCE.md`.

## Loader verdict: ordinary MZ, no packer to peel

`tools/game_triage.py` classifies the program as **MZ (plain real-mode)**, with 129 relocations and entry `0000:2D4E`. The 64-paragraph header puts the load image at file offset `0x400`; the entry is therefore file offset `0x314E`. The MZ page fields (`84` pages, `250` bytes on the last page) account exactly for the 42,746-byte file. The repository's LZEXE, PKLITE and LE/DOS-extender signatures do not match this file.

`tools/decompile_mz.mjs` loads the image at linear base `0x10000` under `x86:LE:16:Real Mode`. The DOS entry at `0x12D4E` asks INT 21h for the DOS version (`AH=30h`), lays out/relocates its runtime stack and memory block, initializes runtime state, then hands off to the application routine at `0x10010`. The Microsoft C run-time marker is present in the image (`MS Run-Time Library - Copyright (c) 1990, Microsoft Corp`). This is a real-mode program, not a protected/packed stub; the interesting code is the programmer itself.

## What the image says the program does

Embedded strings identify the product as **“BA1FB AT90SXXXX PC BASED PROGRAMMER V1.60”**, copyright 1997–1999 Jerry Meng. A separate debug-export string says “Generated by BA1FB AVR Programmer V1.10,” which is inconsistent with the V1.60 banner and is best treated as a stale embedded string, not a second proven version.

The visible device groups are `AT90S1200`, `AT90S2313`, `AT90S2323/2343`, `AT90S4414/4434`, and `AT90S8515/8535`. The profile table in the disassembly assigns corresponding Flash/EEPROM extents of `0400/0040`, `0800/0080`, `0800/0080`, `1000/0100`, and `2000/0200` bytes. These are the application's address limits, not a claim that all members of a grouped family are electrically interchangeable.

The CLI usage string is `FBPRG [FLASH HEX FILE] (EEPROM HEX FILE)`. The text UI offers load/display/program/read/save operations for Flash and EEPROM, device-code readout, setup, a schematic view, reset toggling, and AVR Studio `DEBUG.OBJ`/`DEBUG.ASM` generation. The configuration UI exposes two lock-protect options, printer-port selection, device selection, and the RC option for the 2323/2343 group.

## The diagram and the port mapping agree

`avrprogrammer.zip` contains `avrprogrammer.gif`, a schematic sheet with 8-pin, 20-pin and 40-pin AVR sockets plus a generic 25-pin printer-port wiring. The generic DB-25 drawing labels these connections:

| AVR signal | PC DB-25 | Port direction / code evidence |
|---|---:|---|
| RESET | 6 (data D4) | Output data-register mask `0x10`; set/clear helpers at `0x126E6` / `0x12702` |
| MOSI | 7 (data D5) | Output mask `0x20`; set/clear helpers at `0x1271E` / `0x1273A` |
| SCK | 8 (data D6) | Output mask `0x40`; set/clear helpers at `0x12756` / `0x12772` |
| MISO | 10 (ACK) | Input from status port `base+1`, testing bit `0x40` in `0x127C6` |
| GND | 25 (ground) | Explicitly shown in the schematic |

The two sides corroborate one another: the GIF labels MISO on pin 10/ACK, and the code reads bit 6 from the printer status register. The generic input/output wrappers are at `0x145E6` (`IN`) and `0x145F4` (`OUT`); a mutable base-port word is used by the helpers. This is actual DOS port I/O, not a call to a printer driver or BIOS INT 17h. No port operation was executed during this analysis.

## Bit-banging and the AVR command path

At `0x123F2`, the byte-transfer routine iterates eight times, builds the received byte at bit positions `7-i`, samples the input, and chooses MOSI high/low for each outgoing bit. That is an MSB-first serial shift loop. The SCK and MOSI masks are kept in an output shadow byte before writing the parallel-port data register; RESET has its own D4 helper.

The entry-to-programming routine at `0x12314` establishes the port state, waits through a 200-iteration timing loop, transitions RESET/SCK, and sends the serial programming-enable bytes `AC 53`. It then clocks `FF` and checks for the `53` response, repeating the enable attempt up to 32 times. That explicit handshake is particularly useful: the program is not merely loading Intel HEX into a file buffer; it checks whether the AVR answers on the wired MISO/ACK line before it proceeds.

Selected operation paths, with their literal command bytes and code addresses:

| UI operation | Code path | What the disassembly shows |
|---|---|---|
| Enter programming mode | `0x12314` → `0x123F2` | Sends `AC 53`, clocks `FF`, expects `53` |
| Erase Flash + EEPROM | `0x121B6` | Sends `AC 80 00 00`, then waits using the PIT-based delay routine |
| Program Flash byte | `0x12100` | Chooses `40` or `48`, sends address high/low and data, then reads back through `0x12076` for comparison |
| Read/verify Flash byte | `0x12076` | Chooses `20` or `28`, sends address and returns the sampled byte |
| Program EEPROM byte | `0x12162` | Sends `C0`, address high/low and data, then compares the result from `0x120C0` |
| Read/verify EEPROM byte | `0x120C0` | Sends `A0` plus the address and returns the sampled byte |
| Lock-protect controls | `0x121F4`, `0x1222C` | Distinct `AC E2` / `AC E4` command sequences are selected by the two UI flags |
| RC option (device index 2) | `0x12264`, `0x1229C` | Selects between `AC A0` and `AC A1` for the 2323/2343-only UI option |

These are command bytes observed in the executable; this note does not substitute for an AVR data sheet or a hardware protocol capture. In particular, no target device was attached to validate electrical polarity, timing margin, or chip-specific behavior.

The waits are also visible in code. `0x125F2` latches/reads the PC's PIT channel 0 through ports `0x43` and `0x40` and loops on counter changes; the bit-bang path calls these timing routines between transitions. This is a DOS-era timing strategy that depends on the machine/emulator's timer and parallel-port behavior.

## Reproduction and limits

After extracting `fbprg16.exe` from the archived ZIP to a temporary path:

```sh
python3 tools/game_triage.py /tmp/fbprg16.exe
node tools/decompile_mz.mjs /tmp/fbprg16.exe entry
node tools/decompile_mz.mjs /tmp/fbprg16.exe 0x12314,0x123f2,0x127c6,0x145e6,0x145f4
node tools/decompile_mz.mjs /tmp/fbprg16.exe entry --list 0x12314:0x123e4
```

The Ghidra-WASM decompiler and local SLEIGH specs are already vendored in the repository, so this is an offline static pass. The extracted executable, decompiler output and the GIF used for visual inspection stayed under ignored `.relay/`; no binary or generated analysis dump is added by this register entry.

Still open: the three-byte `FBPRG.CFG` layout; the stale V1.10 debug-export string; hardware verification; and the separate `AVRSETUP.EXE` / `HEXCSUM.EXE` in `avrsetup.zip`. This pass is intentionally scoped to the byte-identical `FBPRG16.EXE` and its evidenced protocol/wiring.
