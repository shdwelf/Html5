# FOUR CORNERS on calculators — native port

`four-corners.xdc` is a 337 KB webxdc bundle whose payload is Three.js
drawing the only place four US states meet: the surveyed quadripoint, the
Navajo volcanic field's minette necks, the San Juan energy basin, the uranium
legacy, and the ancestral Puebloan core around Chaco Canyon. This directory is
the same map on three graphing calculators: **one integer-only C core**,
compiled by sdcc for the Z80, by TIGCC/GCC4TI for the 68k, by gcc for the host
tests, and transpiled to an ES module for `four-corners-calc.html` — so the
browser preview is not a re-implementation of the port, it *is* the port.

```
TI-83 / TI-83+ / TI-84+   Z80   96x64     .8xp
TI-89 / TI-89 Titanium    68k   160x100   .89z
TI-92 / TI-92 Plus        68k   240x128   .9xz
```

No float, no libc, no malloc, no `struct`, 6105 bytes of data — 24.8 % of a
TI-83's practical program budget.

## What survived the trip

The source app has a 3D terrain mesh, state tints, orbit controls, a view
menu, a search palette and a minimap. A 96x64 1-bit LCD has room for none of
that, so the port keeps the **data and the geometry** and throws away the
theater:

| # | Screen | What it shows |
|---|--------|---------------|
| — | boot | `FOUR CORNERS`, device, LCD size, feature counts, the 1/2000° grid note |
| 1 | map | plan view of the quadripoint frame: state lines, the river, markers. `◄ ►` step through visible features, `▲ ▼` zoom 1–8×, `ENTER` dossier, `F1` section |
| 2 | section | relief profile along the selected corridor (or a W–E transect) with the buried feature hung at its true depth on a log ramp. `▲ ▼` depth gain ×5/10/20/40, `F1` swaps route ↔ transect |
| 3 | layers | all 8 layers with feature counts and checkboxes. `▲ ▼` move, `ENTER` toggle, `F1` all-on / defaults |
| 4 | dossier | name, kind, layer, evidence tier, elevation, depth in m and ft, position in degrees, the one-line story, and the data-provenance footer |
| 5 | device | model, CPU, LCD, RAM, table sizes, quantisation |

`1`–`5` jump straight to a screen; `CLEAR`/`ESC` exits. The port uses eight
keys total, which is what all three keypads have in common.

**Evidence tier survives as line style**, since there is no colour to carry it:
official = solid line / filled marker, community = dashed / hollow, context =
dotted / 3-pixel diagonal. And the two schematic depths — the Greater Aneth
oil reservoir at −1700 m and McElmo Dome's CO₂ at −2400 m — hang under the
terrain line on the same log ramp the SOCAL port uses.

## The data pack

`tools/xdc2c.py` does the conversion. It does **not** scrape the bundle with
regexes: it unzips the `.xdc`, runs the app's own ES modules under node
(`tools/fc_dump.mjs`) and emits `core/fcdata.{c,h}` from the live objects, so
a rename in the source app produces a build error rather than a silently
wrong map.

```
 74 features    3 corridors · 24 sites · 47 register rows
 19 vertices    2 state lines + the San Juan River polyline
 31 control points   the curated IDW relief field
  8 layers      4572 B string pool, 215 unique strings
```

Coordinates are quantised to **1/2000°** (worst case 22.3 m) and stored as
`u16` offsets from `-110.600, 35.800`, a 5600 x 4200 frame — 249 km wide by
234 km tall, the whole quadripoint neighbourhood at zoom 1. The surveyed
quadripoint itself lands on `(3110, 2398)` in those units, and the monument's
own register row sits within 2 quantisation steps of it, which the self test
asserts.

Dropped on the way: state tints and the 3D mesh (the section screen's profile
*is* the terrain on a 1-bit LCD), full stories and sources (64 chars of story
per feature survive), the view menu, search and minimap, layer colours, and
691 KB of Three.js. The converter prints the full ledger, table by table,
with the per-device budget check on every run.

## The terrain is the app's own terrain

`js/four-corners-geo.js` defines `elevAt(lon, lat)` as inverse-distance
weighting over 31 curated control points — power 2.4, snap inside 0.5 km —
all in doubles. `tools/xdc2c.py` lifts those constants out of the source (and
raises `SystemExit` with a fix-me message if the power or snap radius
changes), and `core/geo.c` re-derives the same field in Q-format integers:
weights normalized into `[4096, 8191]` before the num/den so both stay inside
32 bits, a 257-entry Q16 `2^(-i/256)` table doing duty for the fractional
power, and `fc_isqrt32`.

The host suite checks the result against **221 samples of the original
function** captured in `host/elevfix.h`:

```
mean |error|   2 m
worst error   13 m       (assertions allow 25 m / 6 m)
```

So Shiprock on the TI-83 is the app's Shiprock (2187 m), not a new one.

## Layout

```
four-corners-calc/
  core/
    fourcorners.h  port contract: screens, classes, line styles, prototypes
    fcdata.h/.c    generated by tools/xdc2c.py — the map itself
    fctables.c     generated by tools/gen_tables.py — Q16 exp2
    geo.c          the IDW relief field, depth ramp, and the map viewport
    app.c          the six screens and the key dispatch
  plat/
    ti83/          Z80: crt0.asm + lcd.asm (copied from calc/, unmodified) + main.c
    ti89/ ti92/    68k: TIGCC main.c
  host/            self test (47 checks), PBM previews, golden dumps
  tools/
    xdc2c.py       .xdc -> core/fcdata.{c,h}   (runs the app's own modules)
    gen_tables.py  regenerates core/fctables.c
    fc_dump.mjs    node side of xdc2c.py
    js_dump.mjs    node mirror of `fcorner-host dump`, for the differential test
  devices.json     the three targets: LCD, CPU, container, type ids
  build.json       retargets calc/tools/build_device.py at this port
  Makefile         host / web / test / preview / pack / data / per-device
```

### What is *not* here

There is no `fb.c`, no `util.c` and no `tables.c` in this directory. The 1-bit
framebuffer, the integer helpers and the 3x5 font come straight out of
`../calc/core/` and are compiled unforked — see `build.json`. The four Python
tools in `../calc/tools/` are shared the same way; each one takes a flag that
points it at this port:

```sh
python3 ../calc/tools/c2js.py <srcs> --out F --globals A,B --banner "TEXT"
python3 ../calc/tools/ti_pack.py --devices devices.json --app FCORNER pack
python3 ../calc/tools/build_device.py --root . --all
python3 ../calc/tools/difftest.py --host H --core C --devices ti83,ti89,ti92 --jsdump P
```

The variable names differ from SITEK and SOCAL (`FOURCRNR` / `fourcrnr`), so
all three ports can live on one calculator at the same time.

## Build

Everything verified in this repo needs only gcc, python3 and node:

```sh
make -C four-corners-calc            # host build + transpiled web core
make -C four-corners-calc test       # 47 core checks, C/JS diff test, container selftest
make -C four-corners-calc preview    # PBM frames for every device (build/preview)
make -C four-corners-calc data       # re-derive the tables from ../four-corners.xdc
```

Calculator binaries need a cross toolchain; missing ones are reported and
skipped, never faked:

```sh
make -C four-corners-calc ti83       # needs sdcc + ti83plus.inc in plat/ti83/
make -C four-corners-calc ti89       # needs tigcc (or gcc4ti)
make -C four-corners-calc ti92
```

## What is verified, what is not

Verified on every `make -C four-corners-calc test`:

* **47 core self checks** — every table offset and string offset in range,
  every vertex and node inside the frame, the integer path length within 8 %
  of the app's own `pathKm()`, the state lines measuring the surveyed
  234/249 km, the elevation field against the 221 captured samples, every
  device rendering every screen inside `FB_MAX`, a full lap of the selection
  returning to its start, the selection on screen at every zoom, and both
  schematic depths surviving into the dossier.
* **`difftest.py`** — the gcc build and the transpiled JS build produce
  byte-identical dumps for all three devices, 80 lines each, including every
  rendered framebuffer hash. That is the check that keeps
  `four-corners-calc.html` honest.
* **Container round-trip** for `.8xp`, `.89z` and `.9xz`.

**Not verified here.** Neither sdcc nor tigcc is installed in this environment,
so **no `.8xp`, `.89z` or `.9xz` binary has ever been assembled, linked or
run** — not by this port, and not on hardware or in an emulator. What exists
is the C that those compilers would consume, the platform glue, and the
container writer. `build_device.py` detects the missing compiler, says so,
and exits 0 rather than producing anything. Expect to fix include-file names
against your copy of `ti83plus.inc` and the linker flags against your sdcc
version.

## Accuracy

Everything on these screens is a generalization. The relief is the app's own
**curated IDW control-point field — explicitly not a DEM** (the boot screen
and the dossier footer both say so), positions are quantised to ~22 m, depths
are schematic values on a log ramp, and the register is the GNIS seed
curated by the source app, not a survey product. The San Juan River measures
**254 km** here — the length of the app's own generalized polyline, not the
river's true 616 km — and the self test pins it so nobody "fixes" the
geometry to chase the published figure.
