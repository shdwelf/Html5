AVR
Firmware Walk

A bootloader is the code that decides whether a machine accepts new firmware — so the question a boot-chain review actually has is: which flash-write sites can a redirect reach? This page decodes the image, walks it from the reset vector, and answers that per SPM site. The decoder is the same js/avrdis.js the tools use, and it is checked instruction-for-instruction against avr-objdump output that upstream itself published — node tools/verify_avrdis.mjs fails if that stops being true.

Self-programming and control-flow sites

SPM writes flash: it is page erase, page fill and page write for the bootloader's own update path, and it is the operation the chipset lock in rtl/ gates on the host side. A site marked dead is decoded and real but cannot be reached from the reset vector or from either side of any conditional — a latent write primitive rather than a live update path.

What this page does and does not do

  • It does not decompile to C. The vendored Ghidra-wasm bridge cannot decompile AVR8 — its LoadImageXml reads outside the word-addressed code space and returns DataUnavailError. That is reproduced by node tools/ghidra_avr.mjs … --probe (0/36 combinations) rather than hidden, and it is why the walk here is done by decoding instructions instead of by a decompiler.
  • The decoder is not self-certified. tools/verify_avrdis.mjs compares it against the avr-objdump listing upstream shipped with Optiboot 8.0: 225/225 instructions, 78/78 branch and call targets resolved by objdump itself, and the symbol table of that listing.
  • The walk is conservative, and that is deliberate. It follows the reset vector and both sides of every conditional and skip instruction. Indirect jumps (ijmp/icall) end a path instead of being guessed, so "reachable" is a lower bound: a site this page calls dead is unreachable by static control flow, while a site it calls reachable is reachable in the image's own terms (interrupt vectors are only scanned for an image loaded at address 0 — a bootloader has none).
  • This is the stand-in for vendor firmware. The MAKInterface / MAKInterface Pro images could not be retrieved — the host refuses connections from this environment and the archives are blocked or gone (samples/avr/PROVENANCE.md records that). These two bootloaders are the same class of code the device would run, and both are verified the same way.
