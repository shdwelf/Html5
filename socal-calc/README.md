# SOCAL SUBSURFACE on calculators — native port

`socal-subsurface.xdc` is a 370 KB webxdc bundle whose payload is 691 KB of
Three.js drawing an animated 3D theater of Southern California's buried
infrastructure. This directory is the same map on three graphing calculators:
**one integer-only C core**, compiled by sdcc for the Z80, by TIGCC/GCC4TI for
the 68k, by gcc for the host tests, and transpiled to an ES module for
`socal-calc.html` — so the browser preview is not a re-implementation of the
port, it *is* the port.

```
TI-83 / TI-83+ / TI-84+   Z80   96x64     .8xp
TI-89 / TI-89 Titanium    68k   160x100   .89z
TI-92 / TI-92 Plus        68k   240x128   .9xz
```

No float, no libc, no malloc, no `struct`, 8584 bytes of data — 35 % of a
TI-83's practical program budget.

## What survived the trip

The source app has six 3D views, orbit controls, x-ray/wireframe modes, five
floating panels and a colour legend. A 96x64 1-bit LCD has room for none of
that, so the port keeps the **data and the geometry** and throws away the
theater:

| # | Screen | What it shows |
|---|--------|---------------|
| — | boot | `SOCAL SUBSURFACE`, device, LCD size, feature and vertex counts |
| 1 | map | plan view of the basin: coast, corridors, rings, sites. `◄ ►` step through features, `▲ ▼` zoom 1/2/4/8×, `ENTER` dossier, `F1` section |
| 2 | section | terrain profile along the selected route with the line hung at its true depth on a log ramp. `▲ ▼` depth gain 5/10/20/40×, `F1` swaps along-route for a W–E transect |
| 3 | layers | all 20 layers with feature counts and checkboxes. `▲ ▼` move, `ENTER` toggle, `F1` all-on / defaults |
| 4 | dossier | name, layer, evidence tier, length + tunnelled %, or area, depth in m and ft, position in degrees |
| 5 | device | model, CPU, LCD, RAM, table sizes, quantisation |

`1`–`5` jump straight to a screen; `CLEAR`/`ESC` exits. The port uses eight
keys total, which is what all three keypads have in common.

**Evidence tier survives as line style**, since there is no colour to carry it:
official = solid line / filled marker, community = dashed / hollow, context =
dotted / 3-pixel diagonal. That is the one piece of the original's legend that
had to be re-encoded rather than dropped.

## The data pack

`tools/xdc2c.py` does the conversion. It does **not** scrape the bundle with
regexes: it unzips the `.xdc`, runs the app's own ES modules under node
(`tools/socal_dump.mjs`) and emits `core/socaldata.{c,h}` from the live
objects, so a rename in the source app produces a build error rather than a
silently wrong map.

```
117 features   25 corridors · 77 sites · 15 rings
581 vertices   266 route + 300 ring + 15 coast
 20 layers     4782 B string pool, 238 unique strings
```

Coordinates are quantised to **1/2000°** (worst case 27.7 m) and stored as
`u16` offsets from `-121.300, 32.500`, a 14320 x 11500 frame. That precision is
theatre against the underlying data — the routes are already 5–15 km
generalizations — but it costs 4 bytes a vertex and it keeps every arithmetic
op inside 32 bits.

Dropped on the way: layer colours (no colour), facts and sources prose, CLUI
captions, the SAR swath rectangles, one off-frame feature, and 691 KB of
Three.js. `python3 tools/xdc2c.py --report-only` prints the full ledger,
table by table, with the per-device budget check.

## The terrain is the app's own terrain

`js/socal-geo.js` defines `elevationAt(lon, lat)` as a sum of rotated Gaussian
bumps plus two sine "fractal" terms, all in doubles. `tools/xdc2c.py` lifts
those literals out of the source (and raises `SystemExit` with a fix-me message
if their shape changes), and `core/geo.c` re-derives the same field in Q-format
integers: a 257-entry Q12 sine table at 256 steps/turn, a 130-entry Q8
exponential, and `sc_isqrt32`.

The host suite checks the result against **221 samples of the original
function** captured in `host/elevfix.h`:

```
mean |error|   2 m
worst error   16 m       (assertions allow 25 m / 5 m)
```

So the mountain on the TI-83 is the app's mountain, not a new one.

## Layout

```
socal-calc/
  core/
    socal.h        port contract: screens, feature classes, line styles, prototypes
    socaldata.h/.c generated by tools/xdc2c.py — the map itself
    sctables.c     generated by tools/gen_tables.py — Q12 sine, Q8 exp
    geo.c          the elevation field, depth ramp, and the map viewport
    app.c          the six screens and the key dispatch
  plat/
    ti83/          Z80: crt0.asm + lcd.asm (copied from calc/, unmodified) + main.c
    ti89/ ti92/    68k: TIGCC main.c
  host/            self test (36 checks), PBM previews, golden dumps
  tools/
    xdc2c.py       .xdc -> core/socaldata.{c,h}   (runs the app's own modules)
    gen_tables.py  regenerates core/sctables.c
    socal_dump.mjs node side of xdc2c.py
    js_dump.mjs    node mirror of `socal-host dump`, for the differential test
  devices.json     the three targets: LCD, CPU, container, type ids
  build.json       retargets calc/tools/build_device.py at this port
  Makefile         host / web / test / preview / pack / data / per-device
```

### What is *not* here

There is no `fb.c`, no `util.c` and no `tables.c` in this directory. The 1-bit
framebuffer, the integer helpers and the 3x5 font come straight out of
`../calc/core/` and are compiled unforked — see `build.json`. The four Python
tools in `../calc/tools/` are shared the same way; each one takes a flag that
points it at this port:

```sh
python3 ../calc/tools/c2js.py <srcs> --out F --globals A,B --banner "TEXT"
python3 ../calc/tools/ti_pack.py --devices devices.json --app SOCAL pack
python3 ../calc/tools/build_device.py --root . --all
python3 ../calc/tools/difftest.py --host H --core C --devices ti83,ti89,ti92 --jsdump P
```

Two bugs in that shared runtime only showed up once a second app used it, and
are fixed in `calc/core/fb.c`: `fb_textm(..., PX_CLEAR)` cleared the glyph
*and* its background, so every inverse-video label was a blank rectangle; and
the `+` and `/` glyph indices were transposed, which nothing noticed until a
screen needed to print `1/2000`.

## Build

Everything verified in this repo needs only gcc, python3 and node:

```sh
make -C socal-calc            # host build + transpiled web core
make -C socal-calc test       # 36 core checks, C/JS diff test, container selftest
make -C socal-calc preview    # PBM frames for every device (build/preview)
make -C socal-calc data       # re-derive the tables from ../socal-subsurface.xdc
```

Calculator binaries need a cross toolchain; missing ones are reported and
skipped, never faked:

```sh
make -C socal-calc ti83       # needs sdcc + ti83plus.inc in plat/ti83/
make -C socal-calc ti89       # needs tigcc (or gcc4ti)
make -C socal-calc ti92
```

## What is verified, what is not

Verified on every `make -C socal-calc test`:

* **36 core self checks** — every table offset and string offset in range,
  every vertex inside the frame, the integer path length within 8 % of the
  app's own `pathKm()`, the elevation field against the 221 captured samples,
  every device rendering every screen inside `FB_MAX`, a full lap of the
  selection returning to its start, the selection on screen at every zoom.
* **`difftest.py`** — the gcc build and the transpiled JS build produce
  byte-identical dumps for all three devices, including every rendered
  framebuffer hash. That is the check that keeps `socal-calc.html` honest.
* **Container round-trip** for `.8xp`, `.89z` and `.9xz`.

**Not verified here.** Neither sdcc nor tigcc is installed in this environment,
so **no `.8xp`, `.89z` or `.9xz` binary has ever been assembled, linked or run**
— not by this port, and not on hardware or in an emulator. What exists is the
C that those compilers would consume, the platform glue, and the container
writer. `build_device.py` detects the missing compiler, says so, and exits 0
rather than producing anything. Expect to fix include-file names against your
copy of `ti83plus.inc` and the linker flags against your sdcc version.

One number the map reports is worth knowing about: the Colorado River Aqueduct
measures **312 km** here, not the 389 km usually published. That is not a
rounding error — it is the length of the app's own 10-vertex generalized
polyline, and the self test asserts it so nobody "fixes" the geometry to chase
the published figure.

## Accuracy

Everything on these screens is a generalization of a generalization. Routes are
5–15 km simplifications, positions are quantised to ~28 m, depths are a log
ramp, and three layers are explicitly marked *community* or *context* evidence
— one of them ("local memory, uncorroborated") is off by default. The dossier
footer says the only thing that matters:

> **CALL 811 BEFORE YOU DIG**
