## 3. What static inspection actually established

### netscream: linked AES-IGE, not the README's introductory “AES-CBC”

`readelf -d/-Ws` on the exact `dist/bin` shows `libcrypto.so.1.0.0` and unresolved external symbols `AES_ige_encrypt`, `AES_set_encrypt_key`, `EC_GROUP_new_by_curve_name`, `EC_POINT_mul`, and `BN_mask_bits`. `objdump -d` of that *original* ELF shows a **call to `AES_ige_encrypt@plt` at `0x401319`** preceded by `AES_set_encrypt_key@plt` at `0x4012e8` with an immediate `0x100` (256 bits). It also shows `BN_mask_bits@plt` called at `0x401588` after a `0xf0` (240-bit) argument. The [organizer `src/crypto.c`](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/crypto/netscream/src/crypto.c) actually calls `AES_ige_encrypt(..., AES_ENCRYPT)`; [`src/screamos.c`](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/crypto/netscream/src/screamos.c) writes **32 bytes of IV first**, then encrypts the zero-padded input and writes the ciphertext. The [README](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/crypto/netscream/README.md#netscream) opens with “AES-CBC” but subsequently states **AES-IGE**; the executable call and source take precedence. Substituting AES-CBC in a recipe would be incorrect.

[Source `src/dualec.c`](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/crypto/netscream/src/dualec.c) initializes `NID_X9_62_prime256v1` and, when the value exceeds 30 bytes, `BN_mask_bits(x, 30*8)` **keeps the low 240 bits**, then writes those 30 bytes; the second call contributes two bytes to a 32-byte output. This conflicts with the README's later `msb30(r0)` description. [`src/crypto.c`](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/crypto/netscream/src/crypto.c) sets `drbg_size = 0` in `drbg_generate` but reseeding sets the shared global `drbg_size = 32`, so its AES counter loop (`for (; drbg_size < 32; …)`) is **skipped after the forced reseed**. The IV and next key therefore expose consecutive Dual EC output rather than the intended AES-DRBG output. That control-flow conclusion is source-backed, not a claim to have recovered a seed or `d`-derived key. A [third-party solution](https://ctftime.org/writeup/15518) describes the intended state-recovery attack, but was not used as a substitute for inspecting distributed bytes.

**Independent known-key vector, NOT a competition solve:** using the organizer's published `key` and `dist/enc` (each hash-pinned above), an off-kitchen Node/OpenSSL AES-256-ECB primitive implements IGE decryption block by block: `Pᵢ = AES⁻¹ₖ(Cᵢ XOR Pᵢ₋₁) XOR Cᵢ₋₁`, starting with `C₀ = IV[0..15]` and `P₀ = IV[16..31]`. It reproduces the organizer's 32-byte `flag` file SHA-256 `24de1a1551e565c890209b5e0a8985a53a5ac69749e126d25fa205f2e489a18b` (test below). **No Dual EC backdoor enumeration, 2-byte completion, point recovery, or AES key recovery was performed.** The local kitchen has no AES-IGE mode and no Dual EC key-recovery operation. Its password-based AES-CBC/GCM and toy XOR recipes cannot stand in for either.

### SOMBRERO ROJO: XOR, SHA-256, RC4; aliases are not algorithms

`readelf -h` on the **unaltered** sample shows the suspicious `ELF64` header declares **big-endian** (`EI_DATA=2`) although the x86-64 `e_machine` field is byte-swapped; further header fields run past EOF. This matches the [organizer README](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/reversing/SOMBRERO_ROJO/README.md). Do **not** claim a correct auto-loaded ELF or an ELF xref map from this file. Native FindCrypt uses Ghidra **raw BinaryLoader, base 0, no auto-analysis**, covering every original byte; Ghidra’s raw address equals a **file offset**, not an ELF virtual address. Any future normalized-header variant needs its own derived-file hash and explicit change log.

The [organizer `ctf_main/main.c` constructor](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/reversing/SOMBRERO_ROJO/ctf_main/main.c#L204-L290) XORs an encoded path with `0xfb`, checks a key file and XORs two other byte arrays with `0xfb` before printing one and passing the pair into `gen_kek_key`. The exact 32-byte encoded `b64_flag_enc` array occurs in the distributed executable at **file offset `0x96d40`**, and a different 33-byte `encrypted` debug buffer occurs at `0x96bf0`; shorter constructor arrays are split across compiler immediates, so their source literals are **not** falsely claimed as contiguous binary matches. [`crypto/rc4block.c`](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/reversing/SOMBRERO_ROJO/crypto/rc4block.c) contains a real RC4 KSA/PRGA and `gen_kek_key`, which hashes **printed-text string then Base64-looking string plus the terminating NUL** (its `size_of_new_string` includes `+1`). The [author's `crypto/sha256.c`](https://github.com/fbsamples/fbctf-2019-challenges/blob/4353c2ce588cf097ac6ca9bcf7b943a99742ac75/reversing/SOMBRERO_ROJO/crypto/sha256.c) explicitly defines SHA-256 constants and initial state. This report does **not** claim to extract/decrypt the appended executable; the program's execution path is deliberately not run.

The pinned [FindCrypt database](https://github.com/TorgoTorgo/ghidra-findcrypt/blob/5c2fd5bb50d13a4092da136dc7004becd8129c7b/FindCrypt/data/database.json), SHA-256 `ec3f54412ea1a1ddca05ec39eaa8ad1a9c38ce021297f359dbc0a58b9c7a8897`, contains **126 signatures**. A separate local Python byte-by-byte comparison of that database against the original files found **0** matches in netscream and **3** in SOMBRERO: `SHA256_K` and the byte-identical `SHACAL2_K` at file offset `0x96ea0`, and `BLAKE2_IV` at `0x96fb0` (the same 32-byte little-endian initial state as SHA-256). That local comparison is **not** a native Ghidra/FindCrypt run. Its aliases require source and disassembly review before labeling algorithms; source supports SHA-256 here, **not** SHACAL-2 or BLAKE2. The repository's independent [`scripts/crypto-find.py`](../scripts/crypto-find.py) gives 0 hits in netscream and 3 in SOMBRERO using *different*, short heuristic constants, including a likely unrelated 4-byte `DES S-box-ish` pattern. Do not equate the two scanners' 3-hit totals or infer DES.

The existing `xor` operation gained an **explicit, validated hex-key format** while retaining the old text-key default; this avoids inserting hidden control characters as a “key.” Enter **only** the copied, bounded hex excerpt in the kitchen text box. For netscream, load **only** the 64-byte `dist/enc` data file, not `dist/bin`. ## 5. Native Ghidra/FindCrypt reproducibility and next backlog

The [hash-gated workflow](../.github/workflows/arena-ctftime-ghidra.yml) installs official Ghidra **12.1.4** with the existing pinned archive SHA-256 `ddac49f903da9d5bac833e5cc79395098b9c33cfd3279be5f31bd00387d2d4db`, Java 21, and the pinned signature database. It imports netscream with the ELF loader for auto-analysis plus a **separate full-file raw loader** for signature scanning; it scans SOMBRERO **raw only** due the misleading header. A generated AES-S-box **positive control** must match before interpreting zero hits. The workflow validates all reports with [`tools/summarize_ctftime_ghidra.py`](../tools/summarize_ctftime_ghidra.py), commits only bounded metadata/labels to this same branch, and publishes full disassembly/decompilation **as CI artifact only**, not as unchecked prose. If the workflow has not succeeded, treat native results as **pending**; the local Python and `objdump` checks above are not Ghidra results.

**Next constrained stages:** (1) Review the native report and targeted xrefs for `AES_ige_encrypt`/`BN_mask_bits`, without claiming source/ELF equivalence from symbol names alone. (2) For SOMBRERO, document a one-byte, hash-pinned normalized-header *derived copy* before any ELF auto-disassembly; independently inspect the RC4/SHA-256 call graph and never execute the embedded payload. (3) If implementing netscream key recovery, validate the *low*-240-bit truncation against organizer `d` and `enc` with a test vector, then add an explicit AES-IGE operation and test it against the published debug-key vector; **do not** label the current hexdump a decryptor. (4) Work through the remaining **16 events** from the initial 18 by locating organizer-owned challenge archives, checking licenses/terms, pinning hashes, and recording missing artifacts as such. (5) Only then expand the CTFtime event queue by year and organizer, with a measured coverage ledger. Never infer an individual's participation or IRC identity from a team scoreboard.
