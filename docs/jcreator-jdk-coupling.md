# JCreator and the JDK: a contract that OpenJDK never contained

This is the research note behind `.github/workflows/jcreator-ghidra.yml`. The
Ghidra half — what JCreator's binary actually does — is generated by that
workflow into [`jcreator-jdk-ghidra.md`](jcreator-jdk-ghidra.md). This file is
the half that can be verified without a disassembler, and it was verified
directly against the OpenJDK repositories on 2026-10-01.

## Why JCreator is a Ghidra target at all

JCreator (Xinox Software, 1999–2014) is a Java IDE that is **not written in
Java**. The Tucows listing archived with the 2001 release states it plainly:

> JCreator is written entirely in C++, which makes it fast and efficient
> compared to the Java-based IDEs.

That single fact is what makes it interesting. Eclipse, NetBeans and IntelliJ
are Java programs that talk to the JDK from inside a JVM; their coupling to the
toolchain is ordinary library code. JCreator is a native Win32 PE that has to
find a JDK on a stranger's machine from the outside, then drive `javac.exe` as
a child process and parse its output. All of that is compiled into the
executable, which means the binary is a **primary source for the
Windows/Java integration contract of its era**.

## The contract, as OpenJDK recorded it

A Windows program that wants to run Java has to answer "where is it installed?"
Through JDK 8, the JDK's own launcher answered that from the registry. From
`jdk/src/windows/bin/java_md.c` in `openjdk/jdk8u`:

```c
#define JRE_KEY "Software\\JavaSoft\\Java Runtime Environment"
```

`GetPublicJREHome()` opens that key under `HKEY_LOCAL_MACHINE`, reads
`CurrentVersion` to get a version string, opens the subkey of that name, and
reads `JavaHome` from it. `LocateJRE()` does the same sweep across both
`HKEY_CURRENT_USER` and `HKEY_LOCAL_MACHINE`. The source comments describe the
key set as *"hardwired on Windows"*, and note that the same logic was
duplicated in the Java Control Panel:

> Note: There is a very similar implementation of the following registry
> reading code in the Windows java control panel (javacp.cpl). If there are
> bugs here, a similar bug probably exists there. Hence, changes here require
> inspection there.

So the mechanism JCreator would have used was real, documented in the JDK's own
source, and shared with Sun's own tooling.

## What happened to it

Measured by fetching `java_md.c` from each repository and counting tokens — not
by code search, which indexes these repositories unevenly:

| repo | path | `JRE_KEY` | `JavaSoft` | `RegOpenKeyEx` | `USE_REGISTRY_LOOKUP` | `GetPublicJREHome` |
|---|---|---:|---:|---:|---:|---:|
| `jdk8u` | `jdk/src/windows/bin/java_md.c` | 1 | present | present | 0 | present |
| `jdk11u` | `src/java.base/windows/native/libjli/java_md.c` | 0 | 0 | 0 | 2 | 2 |
| `jdk17u` | same | 0 | 0 | 0 | 2 | 2 |
| `jdk21u` | same | 0 | 0 | 0 | 0 | 0 |
| `jdk` (mainline) | same | 0 | 0 | 0 | 0 | 0 |

Three distinct events:

1. **Between JDK 8 and JDK 11 the implementation was deleted.** By 11 the
   registry key, the API call and the whole body are gone. This is the JEP 220
   / modular-runtime-image era, when the separately installed "public JRE"
   stopped being the thing a launcher looked for.

2. **A fossil survived to JDK 17.** In 11 and 17 the only remaining traces are
   a declaration and a call site, both wrapped in `#ifdef USE_REGISTRY_LOOKUP`:

   ```c
   #ifdef USE_REGISTRY_LOOKUP
   jboolean GetPublicJREHome(char *buf, jint bufsize);
   #endif
   ```

   `USE_REGISTRY_LOOKUP` occurs in exactly one file in the entire `jdk17u`
   tree — `java_md.c` itself. Nothing defines it. It is dead code guarded by a
   macro no build ever sets.

3. **The fossil was swept up in 2024.** Commit
   [`377f2e538ae0fc94fc5483700a3ae70175017741`](https://github.com/openjdk/jdk/commit/377f2e538ae0fc94fc5483700a3ae70175017741)
   (2024-04-26), *"8329862: libjli GetApplicationHome cleanups and enhance jli
   tracing"*, removed the last reference. A later commit,
   [`0fe15d683`](https://github.com/openjdk/jdk/commit/0fe15d683) (2024-10-30),
   *"8343040: Clean up references to JRE in the launcher code"*, finished
   tidying the vocabulary. Mainline `java_md.c` today is 1,187 lines with **zero**
   registry references.

## The part that was never in OpenJDK at all

Here is the gap that makes the binary worth disassembling.

The JDK launcher only ever read the **JRE** key. JCreator does not want a JRE —
it wants `javac`, which only ships in a **JDK**. The sibling registry key
`Software\JavaSoft\Java Development Kit`, with the same
`CurrentVersion` → `<version>\JavaHome` shape, was written by Sun's Windows
installer and read by third-party tools.

Searching `openjdk/jdk8u` for the string `"Java Development Kit"` returns two
hits, and neither is a registry read:

- `jdk/src/share/classes/com/sun/tracing/package-info.java` — prose
- `jdk/src/share/demo/jvmti/hprof/manual.html` — documentation

So the JDK registry key is a contract that:

- Sun's installer **wrote**,
- third-party IDEs **read**,
- the OpenJDK source tree **never contained**, and
- no modern OpenJDK distribution creates at all.

Its only surviving documentation is in the binaries that consumed it. That is
what the Ghidra probe in `tools/ghidra_scripts/JdkToolchainReport.java` goes
looking for: it buckets every string in the executable into `registry`,
`tools`, `jars`, `flags`, `env`, `jni`, `diagnostic` and `process`, records the
cross-references, and then decompiles only the functions that touch those
buckets. If JCreator reads `Software\JavaSoft\Java Development Kit`, the probe
will show the path string, the `RegOpenKeyEx` import, and the function that
joins them.

The `jars` bucket is a dating mechanism in its own right: JDK 1.1 shipped the
compiler classes in `classes.zip`, JDK 1.2 moved them to `lib\tools.jar`. A
2000-era IDE that supports both has to carry both strings.

## "OpenJVM" — a negative result worth recording

The third thread in this investigation was a search for "OpenJVM". It does not
exist, and it is worth writing that down because the name circulates as if it
does. A 2010 Stack Overflow answer, for example, asserts that Sun "open-sourced
[Java] as OpenJVM".

Checked 2026-10-01:

| source | query | result |
|---|---|---|
| archive.org | full-text `openjvm` | **0 items** |
| GitHub | `openjvm in:name` | 3 repositories, all 0 stars |
| GitHub | org `openjvm` | 404 |
| GitHub | user `openjvm` | 404 |

The three repositories are personal projects — one self-described as "an open
study of the java virtual machine", one an OpenJDK 17 Zero build compiled to
WebAssembly. None is an implementation of the name.

"OpenJVM" is a persistent misnomer for **OpenJDK**, whose JVM is called
**HotSpot**. The real artefacts are `openjdk/jdk` (GPL-2.0, ~1.4 GB of history,
100+ sibling repositories including `jdk8u`, `jdk11u`, `jdk17u`, `jdk21u`,
`loom`, `valhalla`, `leyden`). Anyone looking for "the open source JVM" wants
`src/hotspot` inside that tree.

## Result: the probe found it

Run [36865578705](https://github.com/shdwelf/Html5/actions/runs/36865578705)
confirmed the hypothesis. `JCreator.exe` — 4,485,120 bytes, 22,460 functions,
4,663 defined strings, recovered from `Setup.exe` with `innoextract` — reads
exactly the key that OpenJDK never contained.

All three strings resolve to **one function, `FUN_0044dc60`**, referenced from
three consecutive sites:

| string | address | referenced from |
|---|---|---|
| `Software\JavaSoft\Java Development Kit\` | `00681da4` | `0044dc9f` |
| `CurrentVersion` | `00681d94` | `0044dceb` |
| `JavaHome` | `00681d88` | `0044dd42` |

Decompiled, the routine is Sun's own algorithm pointed at the sibling key:

```c
FUN_005b41ba(s_Software_JavaSoft_Java_Developme_00681da4);
iVar2 = FUN_00506710(0x80000002, local_5c, 0x20019);        /* HKLM, KEY_READ */
...
  cVar1 = FUN_005067d0(s_CurrentVersion_00681d94, &local_60);
  if (cVar1 != '\0') {
    FUN_00506730();                                          /* close */
    iVar2 = FUN_00506710(0x80000002, local_5c, 0x20019);     /* reopen at <version> */
    ...
      cVar1 = FUN_005067d0(s_JavaHome_00681d88, &local_64);
```

`0x80000002` is `HKEY_LOCAL_MACHINE`; `0x20019` is `KEY_READ`. Open the key,
read `CurrentVersion`, reopen at that subkey, read `JavaHome` — step for step
the sequence `GetPublicJREHome()` performs in `jdk8u`, with
`Java Development Kit` substituted for `Java Runtime Environment`. A
third-party IDE reimplemented the launcher's documented algorithm against the
one key the launcher never read.

### How it drives the toolchain

JCreator stores tool invocations as templates with `$[...]` substitution:

| tool | template |
|---|---|
| compile | `"$[JavaHome]\bin\javac.exe"` `-classpath "$[ClassPath]" -d "$[OutputPath]" $[JavaFiles]` |
| run | `"$[JavaHome]\bin\java.exe"` `-classpath "$[ClassPath]" $[JavaClass]` |
| applet | `sun.applet.AppletViewer $[FileName]` |
| others | `jdb.exe`, `jar.exe`, `javah.exe`, `rmic.exe`, `appletviewer.exe`, `javadoc` |

The import table settles the execution model: `RegQueryValueExA` (24 xrefs),
`RegOpenKeyExA` (7), `CreateProcessA` (2), `CreatePipe` (3), `PeekNamedPipe`
(3) — discover via registry, run out-of-process, capture stdout through a
pipe. The `jni` probe returned **0**: no `jvm.dll`, no `JNI_CreateJavaVM`,
no in-process VM anywhere in the binary. `JAVA_HOME` is present as a fallback.

The `jars` bucket dates the build: `tools.jar`, `dt.jar`, `rt.jar`, `src.jar`,
`jre\lib\`, `jre\lib\ext\*.*` — and **no `classes.zip`**, so this is a
JDK 1.2+ world. A wizard string confirms the era: *"Select JavaDoc home path
(e.g C:\jdk1.4\docs\)"*.

### What the probe got wrong, and how that showed

Two things worth recording, because both are the pipeline working rather than
failing:

- **Run 1 analyzed the wrong binaries.** The zips contain installers, not the
  IDE. The probe reported `tools 0, jars 0, flags 0, jni 0` for both — a
  correct negative that immediately identified the mistake. `Setup.exe`
  reported compiler id `borlanddelphi` with a 46 KB `CODE` section, which is
  the Inno Setup signature, and `innoextract` then yielded `JCreator.exe`.
- **`FUN_00464900` is a false positive.** It matched the `registry` bucket on
  the substring `javasoft`, but it is the Help menu handler that opens
  `http://www.javasoft.com`. A substring probe surfaces candidates; it does
  not identify them. The real routine had to be found by following xrefs.

`JCreatorSetup.exe` (v1.11) resisted all three extractors — it is an MSVC
self-extractor that `innoextract`, `7z` and `cabextract` all declined. Only
JCreator LE 2.5.0's IDE binary was recovered, so every finding above is from
the 2001 release.

## Method and honesty notes

- Every OpenJDK claim above was checked by fetching the file through the GitHub
  API and counting tokens in it, because GitHub code search reports
  inconsistent `total_count` values on repositories this large — it claimed
  `GetPublicJREHome` had one hit in `jdk21u`, and fetching the file showed zero.
  Where the two disagreed, the file won.
- The Ghidra findings are **not** in this file. They are generated by the
  workflow into `jcreator-jdk-ghidra.md`, from a run whose log is attached to
  the Actions run. Nothing here predicts what the probe will find; if JCreator
  turns out to use `JAVA_HOME` or a config file instead of the registry, the
  generated report will say so.
- Neither binary was executed. No JDK was installed on the runner. The analysis
  is static only.
