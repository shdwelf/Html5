# Drive CyberChef recipe audit — 2026-11-13

**Decision:** Do **not** publish these 31 supplied links as validated recipes. The URL fragments all reproduce the supplier's `pretty` strings, but at pinned CyberChef commit [`d4d96c6c3d2597fef836d81bfc04617d97c681a5`](https://github.com/gchq/CyberChef/tree/d4d96c6c3d2597fef836d81bfc04617d97c681a5), only **3/31** import as the advertised operation-and-argument tuples. An independently executable operation or a plausible book title does not repair an unimportable URL. This is an audit, **not** a replacement recipe pack or a browser compatibility certification.

The local Drive export is deliberately **not** committed. The audited 31-entry JSON is 20,189 bytes with SHA-256 `6f6319cf2321767f2ad2e2264095c6e1784b668652793dca9d928e2a591feacd`. A separate 21-entry export (SHA-256 `60bdb574e00f9e2d80a2d458fea341c1c899753fe5afc2555d878b40c919776d`) has identical first 21 entries, but is **not** substituted for this audit. No actual-source payload, key, signed message, packet, BBS/IRC transcript, or book excerpt is in the export's URLs: none contains `&input=`. The export's `why` fields are supplier hypotheses, not verified source citations.

## Evidence levels and reproduction

1. **Literal URL / source code:** [upstream `Utils.parseURIParams` and `parseRecipeConfig`](https://github.com/gchq/CyberChef/blob/d4d96c6c3d2597fef836d81bfc04617d97c681a5/src/core/Utils.mjs) are called on each supplied URL; [upstream `App.getURIParams`/`loadURIParams`/`setRecipeConfig`](https://github.com/gchq/CyberChef/blob/d4d96c6c3d2597fef836d81bfc04617d97c681a5/src/web/App.mjs) establish how browser loading uses that parser. The URL decoding is lexically equal to `pretty` in **31/31**. Of these, **3 exact** (#6, #20, #22), **13 parse errors**, **15 parsed-but-different** (usually an operation name prefixed by `/`). *Exact* means name and supplied arguments match, **not** that the entire recipe works on a real input. A parse error happens before UI population; a parsed-but-different recipe may cause an unknown-operation error or a partially populated UI. We did **not** run the upstream web UI or the live site.
2. **Supplied tuple / source code:** All **44 distinct operation names** in the supplier's separate `ops` field exist at that commit. Checking those tuples against the upstream [operation constructors, `Ingredient`, and `Operation`](https://github.com/gchq/CyberChef/tree/d4d96c6c3d2597fef836d81bfc04617d97c681a5/src/core) finds **16/31** rows with at least one schema/shape warning (including two non-boolean checkbox values); **16** separate `Find / Replace`/AES `toggleString` arguments are plain strings rather than `{option,string}` objects. Six rows also produce an ingredient validation/assignment error in this direct check (#4, #5, #9, #26, #29, #31). This is a separate check of **supplier tuples**, not a rescue of the broken URLs. The browser can supply defaults for omitted fields; the Node `Recipe` harness does not. Some invalid URL tuples cannot be sent to the UI at all; the remaining schema checks do not prove UI success.
3. **Synthetic execution / controlled input:** [`scripts/audit-drive-cyberchef-recipes.mjs`](../scripts/audit-drive-cyberchef-recipes.mjs) runs labelled, synthetic checks with upstream `Recipe`/`Dish`; it asserts the input and parser checksum. Its **15 labelled fixture observations are not 15 validated recipes**. Most are deliberately the supplier tuple run **outside** URL loading. Its one corrected XPath ingredient and corrected RFC 5322 folding examples are **not** executions of the supplied recipes. Source-level native-regex tests and one simulated browser-default test are also explicitly labelled. There was no testing on a real mystery corpus, Cryptome signature, book cipher specimen, historical key, or downloaded NZB.

### High-confidence corrections versus open work

- Fix serialization first: generate URLs with upstream `Utils.generatePrettyRecipe()` from tested, full configs and verify `parseRecipeConfig()` round trips on the **actual URL**. Avoid silently interpreting `pretty` as evidence of import success. Correct ingredient shape and argument positions using operation schemas, then test each exact link in a real browser with an input fixture.
- Do **not** substitute a corrected chain for the supplied one without changing its name, provenance and verdict. A successful XPath primitive, cipher round-trip, gzip XML pretty-printer or manually supplied `0x99` preimage only proves its **specific** test. Cryptographic claims need valid packet/DER test vectors; signed-message and JWT *verification* need a verifier and trust policy. Unknown-source `why` text is not evidence.
- Source relevance: primary cataloguing distinguishes [Gaines](https://www.gutenberg.org/ebooks/75074) and [Hitt](https://www.gutenberg.org/ebooks/48871) from [Vigenère's alchemical *Fire and Salt*](https://www.gutenberg.org/ebooks/47365); [Baconian theory books](https://www.gutenberg.org/ebooks/70119) are assertions, not successful decryptions. [PAR2](https://parchive.sourceforge.net/docs/specifications/parity-volume-spec/article-spec.html), [OpenPGP](https://www.rfc-editor.org/rfc/rfc4880.html), [yEnc](https://github.com/caronc/newsreap/blob/master/docs/yenc-draft.1.3.txt), [NZB](https://sabnzbd.org/wiki/extra/nzb-spec) and [MIME](https://www.rfc-editor.org/rfc/rfc2045.html) are format specifications: follow their *input representations*, not just familiar operation names.
