# Sneakers original DOS executable · Ghidra-WASM triage · 2026-10-18

## Scope and provenance

Static-only analysis of the original `SNEAKERS.EXE` extracted from the user-supplied `Sneakers_Promotional_Diskette.zip`:

- ZIP: 2,066,643 bytes; SHA-256 `b6e3d2a99de90b6de401a5d8d0023299c632e65ca98246bbe5d4842336f01eef`.
- `SNEAKERS.EXE`: 2,219,117 bytes; SHA-256 `d5738c9a4050d69ca205a03229dad1616d681fbc9312859be3e629f4b3905961`.
- Companion `SNEAK.EXE`: 1,074,631 bytes; SHA-256 `4710858f7be6461a6d3a267cbc2dec8ca2594e70d28695298ecfb682d99f33bb`.

The ZIP entries are the two executables above. `SNEAK.EXE` identifies as LHA SFX 2.12S and contains a compressed member named `SNEAKERS.EXE`. The XDC boots the directly supplied `SNEAKERS.EXE`; it does not execute the SFX companion.

## Which Ghidra was run

Native Ghidra `analyzeHeadless` is not installed in this sandbox, so **there is no official headless-Ghidra project/export for the original Sneakers binary in this report**. The analysis below uses the repository's vendored Ghidra decompiler compiled to WebAssembly through `tools/decompile_mz.mjs`, with the `x86:LE:16:Real Mode` language. It is a useful static triage, not a substitute for native Ghidra's full DOS loader, reference analysis, or analyst naming. The executable was not run during this analysis.

## MZ header and entry point

The original executable begins with a DOS MZ header:

| Field | Value |
|---|---:|
| `e_cblp` / `e_cp` | 141 bytes / 239 pages |
| relocation count | 1,117 |
| header paragraphs | 288 (4,608 bytes; file offset `0x1200`) |
| declared MZ file area | 121,997 bytes |
| declared loaded image | 117,389 bytes |
| bytes after declared MZ area | 2,097,120-byte overlay |
| entry `CS:IP` | `0000:02D8` |
| linear entry used by the helper | `0x102D8` (load segment `0x1000`) |

At the entry, the Ghidra-WASM pseudocode and 16-bit listing show conventional real-mode setup: save segment/stack state, inspect available DOS memory, resize the process block through `INT 21h`/`AH=4Ah`, copy the PSP command tail, clear a memory region, and transfer control. The helper returns a machine-generated `void 0x102d8(void)` with incomplete stack-space tracking; it does not recover meaningful application names.

The entry calls a routine at `0x1043A`. Its disassembly tests FLAGS bits with `PUSHF`/`POPF`, including 32-bit operand prefixes later in the routine. This is consistent with a CPU/FLAGS capability probe, but its exact intended CPU-version classification has not been confirmed. It is **not** an encryption routine. Another decompiled routine at `0x1C184` loops over DOS handle slots and invokes `INT 21h`; it looks like cleanup/handle closing, but the decompiler's autogenerated name and incomplete context prevent a stronger label. A routine at `0x146DB` manipulates 16-bit data and calls an unnamed routine; it was not identified as a cipher.

## Strings and input clues

The original's embedded strings identify the graphics/runtime layer as **GRASP — Graphics Animation System for Professionals**, version `4.00d`, dated July 27, 1992, with John Bridges and Paul Mace Graphics Software copyright strings. The binary contains resource names including `doss.txt`, `sneaklog.clp`, and `dossback.pic`, plus `ifmouseget`, `fakemouse`, `mousedriver`, and `waitkey`. User-facing strings include **“Microsoft-Compatible Mouse Driver Found.”** and **“Press Any Key to Continue.”** These are direct bytes in the original executable; they are not findings from the repository reconstruction.

A printable-string search found no literal `SETEC`, `ASTRONOMY`, `password`, `cipher`, `encrypt`, or `decrypt` string in this original executable. That is a limited string result, not proof about all binary encodings.

## Encryption: corrected result

The repository's earlier reverse-engineering note described XOR `0x5A`, ROT13, Caesar `+7`, a Scrabble/password gate, and `setec astronomy`. Those behaviors belong to the **4,221-byte handcrafted repository reconstruction** and its synthetic accompanying assets. They must not be attributed to the original 2.2 MB executable.

The original `SNEAKERS.EXE` and `SNEAK.EXE` were scanned with `scripts/crypto-find.py`, the repository's dependency-free known-constant heuristic inspired by Ghidra's “Find Crypt” concept. It found **zero known standard crypto constants** in either original. A bounded single-byte-XOR scan for selected known strings also found no matches. `SNEAK.EXE` is LHA compression; that is not encryption. See [`ghidra/sneakers-original-crypto-scan-2026-10-18.md`](ghidra/sneakers-original-crypto-scan-2026-10-18.md).

**Conclusion:** no encryption algorithm has yet been identified in the original Sneakers binary. The static evidence does not rule out custom, table-free, or resource-specific transformations. The previous XOR/ROT13/Caesar claims are not evidence for the original.
