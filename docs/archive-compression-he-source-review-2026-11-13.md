# Archive compression and homomorphic-encryption review — 13 Nov 2026

**Scope.** This is a targeted implementation plus a format/source audit, **not** a universal decompressor or a claim that newer codecs can be substituted into existing file formats. The changed runtime path is `js/zip.js`, the small ZIP32 writer used by Glendora's webxdc export. Separate runnable examples demonstrate bounded-depth ciphertext arithmetic (SEAL/BFV) and a bootstrapped FHE circuit (Concrete). ACE/RAR codecs and the Vault's 7z codec were not replaced.

## Format decisions and implementation boundaries

| Format | What the format accepts / what this repository actually does | Appropriate enhancement and gate |
| --- | --- | --- |
| **ACE** | Proprietary legacy format; CyberChef's `aceHeader` recognizes a header, **not** an ACE decompressor. The external [`seb3773/ace-c`](https://github.com/seb3773/ace-c) project describes a C11 encoder/decoder for ACE 1.0/2.x; this repository holds a [distance-history/CRC correction](ace-delta-history-crc-fix-2026-11-07.md) for that external tree, not a browser ACE codec. Its README's interoperability statements are upstream claims, not independently established here. ACE's CRC variant and solid-history handling differ from ZIP's. | If maintaining an ACE path: keep the patch against a pinned upstream revision, build a mixed STORE/LZ77/blocked/delta/solid corpus, compare authentic **independent** WinACE/UNACE results and CRCs, and sandbox extraction. Do not feed ZIP/DEFLATE bytes to an ACE decoder or announce a compatible encoder based on a self-round-trip. |
| **RAR** | [RAR 5's first-party structure note](https://www.rarlab.com/technote.htm) specifies record layout and points to UnRAR for algorithm details. [libarchive's format matrix](https://github.com/libarchive/libarchive/wiki/LibarchiveFormats) lists RAR/RAR5 **read only**. The pinned [`7z-wasm@1.2.0`](https://github.com/use-strict/7z-wasm) bundles 7zz 24.09 and an unRAR-derived decoder; its license includes the **unRAR restriction** against using that code to recreate a RAR compressor. No RAR encoder or format-wide RAR extraction was added here. | Preserve readable RAR/solid/multi-volume samples, test readers separately and respect the license. Do not describe ZIP, 7z, or an unrelated LZ77 implementation as a RAR compressor. Avoid invoking an external decoder on untrusted input without entry-size/path/resource caps. |
| **ZIP** | [PKWARE APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) defines methods 0 (STORE), 8 (DEFLATE), and optional method 93 (Zstandard; historical 20 was deprecated). **Method registration does not imply old readers implement it**: [Python 3.11's `zipfile`](https://docs.python.org/3.11/library/zipfile.html) supports 0/8, among other methods, but not Zstd ZIP entries. Before this change, `js/zip.js` marked files method 8 but its `rawDeflate` wrote only *uncompressed* DEFLATE blocks (RFC 1951 `BTYPE=00`). Now `deflate:true` uses vendored fflate's actual LZ77/Huffman raw DEFLATE stream (level 6 by default; 0–9 allowed), but chooses method 0 if compression is not smaller. The old stored-block helper remains available. | Keep 0/8 for webxdc/ZIP interoperability; measure codec levels against representative data. Any method 93 experiment must be **opt-in**, documented and tested against actual target readers, never silently written to these `.xdc` bundles. This writer is ZIP32-only: it now rejects overflowing entry counts, UTF-8 filename lengths, sizes, offsets or central-directory length rather than silently truncating; no ZIP64, spanning, encrypted ZIP or streaming API is claimed. |
| **7z** | [7-Zip's format page](https://www.7-zip.org/7z.html) documents LZMA/LZMA2 and solid compression and filters. Here the separate Haiku Vault v2 path uses staged `7z-wasm@1.2.0` (LZMA2) inside an authenticated frame; see `test/vaultfile-v2.test.ts`. This does **not** make the ZIP writer a 7z writer or enable ACE. The upstream [7-Zip 26.01 release](https://github.com/ip7z/7zip/releases/tag/26.01) describes newer optimizations and bug fixes; those are **not** in the pinned 24.09-based WASM package. | For bulk, highly redundant files compare LZMA2 dictionary, solid-block limits and filters (BCJ for executables, Delta for suitable data); measure extraction latency/memory and random-file access, not just final bytes. Upgrade 7zz/WASM only with license, build reproducibility, adversarial-input and independent-reader regression gates. |
| **gzip** | [RFC 1952](https://www.rfc-editor.org/rfc/rfc1952) wraps a DEFLATE payload ([RFC 1951](https://www.rfc-editor.org/rfc/rfc1951)) with a gzip header, CRC-32 and size trailer. It is a sequential stream, **not a multi-file ZIP**. The repo uses gzip for some existing sync artifacts; this PR does not rewrite them. | For `.gz`, tune DEFLATE effort or use an explicit new filename/container for another codec. Brotli ([RFC 7932](https://www.rfc-editor.org/rfc/rfc7932)) and Zstandard ([RFC 8878](https://www.rfc-editor.org/rfc/rfc8878)) are their own formats, not a `gzip -9` mode. Validate exact decompressed bytes and checksums; size alone is not authenticity. |

`tools/archive_inspect.py` relies on Python ZIP tooling for its vendor downloads; it is not a cross-format RAR/ACE/7z extractor. CyberChef's archive-header triage tests are not decompression interoperability tests. The older [recipe matrix](decompressor-recipe-matrix-2026-10-21.md) remains a discovery/triage guide, not a support declaration. Archive extraction needs containment, expansion-ratio, file-count, time and path controls regardless of chosen codec.

### What changed in ZIP and how it was checked

- `js/zip.js` imports the already-vendored browser ESM `vendor/fflate/browser.mjs` (MIT, 0.8.3); there is no browser-facing network request. `sw.js` precaches that import and bumps its cache version for offline exports. Each member's CRC-32 and both ZIP headers use the **selected** method (0 or 8) and corresponding byte lengths. Compression is synchronous and per-member; it deliberately does not promise efficient processing of multi-gigabyte archives.
- `tools/check_ghs.mjs` formerly assumed every method-8 payload was a stored DEFLATE block. Its ZIP directory walker now decodes method 8 using **independent Node zlib** before checking size and CRC. `node tools/check_ghs.mjs` passed **106/106** checks.
- `tests/zip-deflate.test.mjs` checks empty, UTF-8, high-entropy, >65,535-byte and real Glendora `.xdc` members, explicit STORE and levels 0/9, deterministic bytes with a fixed date, and ZIP32 range errors. It reads the writer's central/local headers, decodes via zlib, and tests the whole archive with **Python `zipfile`**, **Info-ZIP `unzip -tqq`**, and the independent **7-Zip WASM ZIP reader**. The Python/Info-ZIP checks run when the respective executables are installed; zlib and 7z-wasm are exercised by the Node test. This is interoperability evidence for tested samples, not a general ZIP conformance proof.

### Reproducible size study (bytes; no timings)

`npm ci && node tools/bench-archive-codecs.mjs --json` uses repository files and a deterministic xorshift entropy control. Node 22.22.3, fflate 0.8.3, 7z-wasm 1.2.0 and the default Node zlib codecs produced:

| Corpus (source; SHA-256 in script output) | Raw | Prior ZIP method 8 / stored blocks | New ZIP `deflate: true`, level 6 | gzip -6 | Brotli quality 5 | Zstd default | 7z LZMA2 -mx5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `docs/decompressor-recipe-matrix-2026-10-21.md` | 4,053 | 4,176 | **2,292** | 2,190 | 2,112 | 2,241 | 2,293 |
| `tools/check_ghs.mjs` | 34,618 | 34,741 | **12,059** | 11,663 | 11,336 | 12,370 | 11,057 |
| `public/apps/cyberchef/index.html` | 1,947,777 | 1,948,045 | **588,128** | 577,153 | 517,880 | 584,766 | 460,609 |
| Seeded 131,072-byte entropy control | 131,072 | 131,205 | **131,190** (method 0) | 131,132 | 131,077 | 131,084 | 131,196 |

The *prior ZIP* column is the exact length implied by the prior writer's `rawDeflate` blocks plus its ZIP32 headers for one `sample.dat` entry, **not** a guessed compression ratio. A separate real Glendora export with `buildModel({boxes:false,simplify:0.6,trees:190})` and grid 22 fell from **256,336** prior bytes to **about 58,190** bytes now (**77.3%** smaller); Python, Info-ZIP and zlib checked its contents. The VRML generator stamps the current time in a header, which can change the compressed size by a few bytes between runs; the four table corpora are fixed. Level 9 is *not* automatically better: for the source corpus level 9 gave 12,061 vs level 6's 12,059 bytes. Comparisons to gzip/Brotli/Zstd/7z include each format's **different wrapper/metadata and reader requirements**; none is an option to substitute into ZIP method 8 or `.gz`. This run is a size study, not a speed claim, and it does not establish a universally optimal codec. To test a separately obtained source file without tracking it: `node tools/bench-archive-codecs.mjs --file /path/to/corpus.txt` (inspect its SHA-256 in output).

## Source-check deep dive: Gutenberg, Archive.org and metasearch

**Project Gutenberg.** The [catalog record for Austen's *Pride and Prejudice*, eBook 1342](https://www.gutenberg.org/ebooks/1342) distinguishes the **754-kB UTF-8 plain text** from a **595-kB no-images EPUB** and a **23.7-MB images EPUB3** (and a 24.1-MB HTML ZIP). Those artifacts have different contents and cannot be read as evidence that one codec beats another. The record says the edition was updated 29 September 2026, credits Chuck Greif/Distributed Proofreaders, and says its underlying images were available at Internet Archive; it does **not** uniquely identify an Archive.org scan in the record. The page labels the text public domain **in the USA**. [Gutenberg's license explanation](https://www.gutenberg.org/policy/license.html) directs people outside the US to check their jurisdiction; neither its text nor the images are committed here. A valid corpus comparison must pin edition URL, retrieval date, byte count, SHA-256, rights, and an identical byte stream across encoders. This PR did **not** download or benchmark the 754-kB original; the benchmark accepts a user-supplied local file instead.

**Internet Archive.** The item [RFC 7932 (Brotli)](https://archive.org/details/rfc7932) and its [metadata](https://archive.org/metadata/rfc7932) distinguish *original* `rfc7932.txt` (397,150 bytes) and PDF (212,629 bytes) from OCR, DJVU, JP2 ZIP and search-text **derivatives**. The [RFC 8878 (Zstandard) metadata](https://archive.org/metadata/rfc8878) lists an original `rfc8878.txt` (112,425 bytes) alongside PDF and generated OCR derivatives. Those derivative sizes are not comparative compression results. Archive.org's item metadata gives source pointers to the RFC Editor, but it is still a **mirror**: [RFC Editor 7932](https://www.rfc-editor.org/rfc/rfc7932) and [RFC Editor 8878](https://www.rfc-editor.org/rfc/rfc8878) are the primary specifications. If reusing an Archive item, inspect `source`/`original` fields, hash the downloaded bytes with SHA-256, compare the primary text, and respect item rights; a catalog MD5 or an OCR version is not a proof of canonicality. No Archive.org corpus files were imported into Git or the tests here.

**Metasearch, 13 Nov 2026.** [`searx.space`](https://searx.space/) is a *directory* of SearXNG instances (73 displayed on this check), not a compression authority. [`libresearch.space` result for ZIP Zstd](https://libresearch.space/search?q=ZIP%20Zstandard%20method%2093%20APPNOTE&categories=general) pointed to PKWARE APPNOTE and Python docs; [`baresearch.org` result for RFC 8878](https://baresearch.org/search?q=RFC%208878%20Zstandard%20APPNOTE%2093) pointed to RFC Editor/Archive.org; [`search.utilibre.org` result](https://search.utilibre.org/search?q=RFC%208878%20Zstandard%20APPNOTE%2093&categories=general) mixed the current RFC 8878 with **obsoleted RFC 8478**. [`utilibre.org`](https://utilibre.org/en/) itself is a tool catalog, not that metasearch endpoint. These are live **discovery leads**, not three independent confirmations: engine overlap, caches, indexing drift and availability affect results. We checked the primary APPNOTE/RFC pages directly. Never submit key material or private source-check contacts to public metasearch queries.

## Homomorphic encryption: working examples and explicit limitations

| Path | Verified in this session | What it does **not** prove |
| --- | --- | --- |
| Existing CyberChef [multiplicative ElGamal demo](cyberchef-elgamal-multiplicative-demo-2026-11-07.md) | Existing tests cover the toy group operation; **not changed here**. | This is *not* FHE, general ciphertext arithmetic, or a production cryptosystem. |
| `npm run demo:bfv` (`tools/he-bfv-demo.mjs`) | `node-seal@7.0.0` wraps Microsoft SEAL 4.1.2. The 128-bit **library parameter-validation setting** passed for BFV, poly degree 4096, batching and its library-selected coefficient moduli. Fresh in-memory keys, public-key encryptions of 3 and 5, **ciphertext + ciphertext = 8**, **ciphertext × ciphertext = 15**, relinearization and decryption worked; multiplication left **14 bits of noise budget** for that sample. `tests/he-bfv.test.mjs` also checked 0×100 and 100×100 and input-domain rejection. | **Leveled/finite-depth HE**, no bootstrapping in this example; 14 noise-budget bits are *not* 14 security bits. The context's 128-bit setting is a library parameter choice, not an independent attack evaluation. All objects coexist in one process; it is not an isolated service or deployed key-management design. No keys are written to disk or printed. |
| `tools/he-concrete-fhe-demo.py` | Optional `concrete-python==2.11.0` with `torch==1.13.1`, run on CPython 3.11 x86-64 Linux. Compiled `(x*y + x + 1)²` using an encrypted multiplication followed by `fhe.LookupTable`; **three programmable bootstraps** reported in the compiled circuit; generated keys, encrypted both inputs, evaluated through `server.run` with *evaluation* keys, decrypted and verified **all 16 pairs** in the fixed domain `x,y∈{0,1,2,3}`. `RUN_CONCRETE_FHE=1 PYTHONPATH=/tmp/concrete-audit/site node --test tests/he-concrete.test.mjs` passed here. | A demonstrable bootstrapped circuit with a library that supports FHE; not arbitrary-length practical compute, a cryptanalysis, a private host/server deployment, or a guarantee about third-party parameters. The client and server API objects are in one process for the example. Its Python dependencies occupied **~3.8 GB** in an untracked `/tmp` install; default `npm test` *skips* this optional integration, not silently simulates it. |

Reproduce the optional FHE integration (large dependency download; do not commit the environment):

```sh
python3.11 -m venv .venv
. .venv/bin/activate
python -m pip install -r tools/he-concrete-requirements.txt
python tools/he-concrete-fhe-demo.py
RUN_CONCRETE_FHE=1 node --test tests/he-concrete.test.mjs
```

The demo uses **no fixed encryption seed**, log of secret keys or key export. The Concrete compiler inputset is a tiny bounded domain; values outside it are not supported by this example. The inspected `node-tfhe@1.8.2` JavaScript `FheUint8` binding exposes encrypt/decrypt but no high-level arithmetic on that class, so it was **not** mislabeled a computing FHE example. Concrete's [first-party quick start](https://github.com/zama-ai/concrete/blob/main/README.md) documents encrypt/run/decrypt and [its key-value example](https://github.com/zama-ai/concrete/blob/release/2.11.X/frontends/concrete-python/examples/key_value_database/key_value_database.ipynb) uses lookups in FHE; the runnable script and bootstrap count above are this repository's separate checks. The [node-seal README](https://github.com/s0l0ist/node-seal) documents its v7 WASM bindings; the examples here are educational only.

## Private source-check boundary

This change does not copy private vCards, contacts, fingerprints, cloud identifiers or source-check reports into Git or its offline bundles, and does not import key material. This PR does **not** establish an independently validated vCard/PGP-keyring pair: a provenance report or an embedded armored public key is not the same thing as a separately verified keyring. Identity, revocation, ownership and trust must be assessed in a private workflow with the requested artifacts and their consent/provenance; do not infer them from filenames or publish them as a shortcut. Keep private material out of public Git (backlog constraint F3).
